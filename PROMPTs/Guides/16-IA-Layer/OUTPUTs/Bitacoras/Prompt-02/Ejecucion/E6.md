## 1. Qué se hizo

1. Se aplicó el Conocimiento v0 (`E4-Conocimiento-v0.md`, sin la guía) a un servicio privado existente en
   producción, para especificar el piloto de C-7.1: consulta en lenguaje natural sobre historial y métricas
   con herramientas tipadas de sólo lectura, inquilino resuelto por el código, sin consulta libre.
2. La especificación, el checklist y el expediente correlativo quedaron en un commit local en una rama
   `g16/*` de `<privado>`, carpeta de especificación propia. No hubo push ni PR.
3. Prioridades U-7.2 registradas: consulta (1), clasificación de fallos (2), redacción asistida (3), RAG (4),
   segmentación (5, sólo diseño, nunca dispara un envío masivo: borrador con confirmación humana, C-7.2).
4. No se corrió modelo (la prueba con modelo de E6 es opcional) ni se tomaron turnos.

## 2. Reglas abstractas K-nn

Hallazgos sobre el Conocimiento v0, generalizados. Son la entrada de E7 (caso → regla).

| K | P | Hueco del v0 | Sección del v0 | Regla propuesta para la v1 |
|---|---|---|---|---|
| K-01 | P1 | No hay regla, requisito ni ítem de checklist para el aislamiento por inquilino; sólo para la sesión | §8, §9, §11 | El inquilino lo resuelve el código antes de llamar al modelo; ninguna firma de herramienta lo recibe; prueba «recurso de otro inquilino → no encontrado»; ítem nuevo del checklist. Vale también cuando el rol del usuario es global y el inquilino sale de un contexto validado |
| K-02 | P1 | Requisitos, ADR de capas y C4 nombran capas de referencia que un servicio existente puede no tener | §3, §8 | En CTX-EXISTENTE, primer paso: tabla de correspondencia capas de referencia → estructura real; los requisitos se reescriben con nombres reales |
| K-03 | P2 | El árbol sólo distingue «proponer» y «actuar»; no hay hoja para usar herramientas sin escribir | §1, §9 | Dos variantes de A1: sólo lectura (sin aprobación; ASI09 no aplica) y con escrituras (aprobación obligatoria) |
| K-04 | P1 | P-8 y el requisito de salida cubren salidas estructuradas; nada ancla una respuesta libre que afirma datos | §2, §4, §8 | Validador determinista: cada valor afirmado en una respuesta libre aparece en un resultado de herramienta de esa conversación; si no, *rechazado* |
| K-05 | P2 | Se especifica una capacidad por vez; no hay inventario con estado ni categoría de acción irreversible de alcance masivo | §6, §2 | Inventario ordenado de capacidades (especificada, pendiente, sólo diseño); una acción irreversible y masiva nunca la dispara el modelo |
| K-06 | P2 | La inyección indirecta se piensa como texto del usuario o de RAG; los datos internos también traen texto de terceros | §9, §8 | La proyección de cada herramienta, también las de lectura, excluye el texto libre de terceros o lo marca no confiable |
| K-07 | P2 | No dice qué hacer si el caso de uso existente no trae el filtro que la pregunta necesita | §4, §10 | La herramienta envuelve sólo lo existente; la brecha va a deuda del producto, no a una consulta nueva dentro de la capa |
| K-08 | P1 | Las ADR mínimas llevan número fijo, que choca con el registro de un proyecto existente | §7 | Las ADR mínimas se nombran por tema; cada proyecto las numera en su registro |
| K-09 | P3 | Falta el requisito de nacer apagada en un servicio en producción | §8 | Requisito base en CTX-EXISTENTE: capacidad apagada por parámetro; apagada no cambia el comportamiento previo |
| K-10 | P3 | El checklist no distingue una decisión escrita de una firmada | §11 | SÍ firmado / SÍ pendiente de firma; PROD exige firma |

**Conteo:** P0 0 · P1 4 · P2 4 · P3 2. Qué sobró: la fila de RAG de la matriz y la frontera con clientes no
aplicaron; el NO APLICA con motivo alcanzó.
